DATABASE ARCHITECTURE NOTE · อ้างอิงการตัดสินใจเลือก Backend

Supabase หรือ Firebase สำหรับระบบข้อสอบ Adaptive Learning

สรุปการเปรียบเทียบทั้งสองแพลตฟอร์ม และวิเคราะห์เจาะจงสำหรับระบบที่ต้องมีการวิเคราะห์ผลสอบ, AI สร้างข้อสอบใหม่จากแนวโน้มความผิดพลาด และรองรับภาพประกอบข้อสอบ

สรุปสั้น

Supabase เหมาะกว่าอย่างชัดเจน เพราะระบบนี้มีข้อมูลเชิงสัมพันธ์ซับซ้อน ต้องทำ analytics หนัก และต้องค้นหาเชิงความหมายด้วย embedding — ทั้งสามอย่างเป็นจุดแข็งของ Postgres ที่ Firestore ทำได้ยากหรือทำไม่ได้เลย

1 · จุดเด่นของ Supabase เทียบกับ Firebase (ภาพรวม)

ฐานข้อมูลแบบ Relational (PostgreSQL)

ความต่างที่ใหญ่ที่สุดคือ Supabase ใช้ Postgres จริง ในขณะที่ Firebase ใช้ Firestore ซึ่งเป็น NoSQL เอกสารต้นฉบับ (document-based) ผลคือ Supabase เขียน SQL ซับซ้อนและ JOIN ตารางได้ มี foreign key และ ACID transaction รองรับ data type หลากหลายอย่าง JSONB, Array, PostGIS และทำความสัมพันธ์แบบ many-to-many ได้โดยไม่ต้อง workaround

Open source และไม่ติด Vendor Lock-in

โค้ด Supabase เปิดให้ดูและ self-host ได้ด้วย Docker ข้อมูลเป็น Postgres มาตรฐานจึง dump แล้วย้ายผู้ให้บริการอื่นได้ทันที ต่างจาก Firestore ที่การ export ข้อมูลออกไปใช้ที่อื่นทำได้ยากกว่า

Row Level Security (RLS)

กำหนดสิทธิ์การเข้าถึงที่ระดับฐานข้อมูลโดยตรง ทำให้ปลอดภัยแม้ query ผ่าน client โดยตรง เป็นมาตรฐานของ Postgres ที่ผ่านการพิสูจน์มายาวนาน ไม่ใช่ DSL เฉพาะของแพลตฟอร์มใดแพลตฟอร์มหนึ่ง

Ecosystem ของ Extension

ติดตั้ง extension เสริมได้ เช่น pgvector สำหรับเก็บ embedding เพื่อ semantic search, PostGIS สำหรับค้นหาตามพิกัด GPS และ pg_cron สำหรับตั้ง scheduled job

ราคาที่คาดเดาได้ง่ายกว่า

Firebase คิดเงินตามจำนวน read/write ทำให้บิลพุ่งเร็วเมื่อ traffic สูง ส่วน Supabase มี pricing แบบ tier ชัดเจน คาดการณ์ต้นทุนได้ง่ายกว่า

ใช้เครื่องมือมาตรฐานได้

เขียน SQL ตรง ๆ หรือใช้ ORM ยอดนิยมอย่าง Prisma และ Drizzle ได้เลย มี Supabase CLI สำหรับรัน local environment และทำ database branching

● SUPABASE ได้เปรียบ

  • SQL relational + JOIN + ACID
  • Open source, ย้ายข้อมูลง่าย
  • RLS ระดับฐานข้อมูล
  • pgvector, PostGIS, pg_cron
  • ราคาแบบ tier คาดเดาได้

● FIREBASE ได้เปรียบ

  • Offline sync บนมือถือ
  • Push notification ผ่าน FCM
  • Mobile ecosystem ครบ (Analytics, Crashlytics)
  • Auth หลากหลาย เช่น phone auth

สรุปภาพรวม: ถ้าโปรเจกต์มีความสัมพันธ์ของข้อมูลซับซ้อน ต้องการ query ที่ยืดหยุ่น หรือกังวลเรื่อง lock-in และบิลพุ่ง Supabase มักเป็นตัวเลือกที่ดีกว่า แต่ถ้าเป็น mobile app ที่เน้น offline-first และต้องการ ecosystem ของ Google ครบ Firebase อาจยังเหมาะกว่า

2 · วิเคราะห์เจาะจง: ระบบข้อสอบ Adaptive Learning

โจทย์คือระบบข้อสอบที่ต้องวิเคราะห์ผลการทดสอบ ให้ AI เสนอข้อสอบชุดใหม่จากการวิเคราะห์ วิเคราะห์แนวโน้มข้อที่มักเจอเมื่อทำผิดในหมวดเดียวกัน และมีภาพประกอบข้อสอบ — ความต้องการทั้งสี่ตรงกับจุดแข็งของ Supabase เกือบทั้งหมด

2.1 โครงสร้างข้อมูลเป็น Relational โดยธรรมชาติ

students ──< attempts >── questions ──< questions_topics >── topics (parent ซ้อนกันได้)
                              │
                              ├── difficulty_level
                              ├── image_url
                              └── embedding (vector)

คำถามแบบ "นักเรียนคนนี้อ่อนเรื่องอะไร และข้อไหนในเรื่องนั้นที่คนผิดบ่อยสุด" คือการ JOIN และ GROUP BY 3–4 ตาราง ทำได้ง่ายใน Postgres แต่ทำยากใน Firestore เพราะต้อง denormalize ข้อมูลซ้ำซ้อนจนดูแลรักษายาก การคำนวณ Adaptive เช่น IRT หรือ Elo rating ต่อหัวข้อ ต้องอ่าน-เขียนหลายตารางพร้อมกันใน transaction เดียว ซึ่ง Postgres รับประกันด้วย ACID ในขณะที่ Firestore ทำ multi-document transaction ได้แต่จำกัดและซับซ้อนกว่า

2.2 การวิเคราะห์ผลและแนวโน้ม = งาน SQL Analytics โดยตรง

การหารูปแบบ เช่น "เมื่อทำผิดข้อในหมวดนี้ มักผิดข้อไหนตามมา" คือการหา co-occurrence pattern ซึ่งทำได้ด้วย GROUP BY, HAVING, window function อย่าง RANK() และ PERCENT_RANK(), และ recursive CTE รวมถึงทำ materialized view เก็บสถิติสำเร็จรูป (error rate ต่อ topic, จุดอ่อนต่อ student) แล้ว refresh ตาม schedule และต่อ BI tool อย่าง Metabase หรือ Grafana เข้ากับฐานข้อมูลได้โดยตรง ในขณะที่ Firestore มีแค่ aggregation พื้นฐาน หากต้องวิเคราะห์จริงจังต้อง export ไป BigQuery เพิ่มท่อข้อมูล ค่าใช้จ่าย และความหน่วง

2.3 AI สร้างข้อสอบใหม่ — จุดที่ pgvector ต่างมากที่สุด

  1. นักเรียนทำข้อสอบ → เก็บ attempts ทุกข้อ
  2. Cron หรือ Edge Function ดึงสถิติ เช่น ข้อที่ผิดบ่อยใน topic X และความยากเฉลี่ยที่เหมาะกับนักเรียนคนนั้น
  3. ส่ง context ให้ LLM ผ่าน Edge Function เรียก OpenAI หรือ Claude API เพื่อสร้างโจทย์ใหม่
  4. ตรวจความซ้ำด้วย pgvector: หาข้อที่มี embedding ใกล้เคียงกับที่เพิ่งสร้าง (WHERE topic_id = X ORDER BY embedding <=> new_embedding LIMIT 5) — filter ตาม metadata และค้นหาเชิงความหมายได้ในคำสั่งเดียว
  5. บันทึกเป็น draft → ครูตรวจ → publish

จุดสำคัญคือขั้นตอนที่ 4: ใน Supabase, embedding อยู่ในตารางเดียวกับโจทย์ ส่วน Firebase ต้องพ่วง vector database แยกต่างหาก เช่น Pinecone หรือ Vertex Vector Search ทำให้เกิดปัญหา sync ข้อมูลและ architecture ซับซ้อนขึ้นชัดเจน

2.4 ภาพประกอบข้อสอบ

ทั้งสองแพลตฟอร์มมี Storage ให้ แต่ Supabase มีข้อได้เปรียบเฉพาะระบบข้อสอบ: Signed URL ผสาน RLS ทำให้รูปข้อสอบเข้าถึงได้เฉพาะคนที่กำลังสอบจริงเท่านั้น ป้องกันการแชร์ลิงก์รูปข้อสอบ ซึ่งเป็น requirement ด้านความปลอดภัยที่สำคัญของระบบสอบ

4 · ข้อควรระวังถ้าเลือก Supabase

  • ต้องออกแบบ schema ให้ดีตั้งแต่ต้น ทีมควรถนัด SQL และการ normalize ข้อมูล
  • AI ที่สร้างข้อสอบควรมี human-in-the-loop — ให้ AI สร้างเป็น draft แล้วให้ครูหรือผู้เชี่ยวชาญตรวจก่อนใช้จริง ทั้งเรื่องความถูกต้องของเนื้อหาและเฉลย
  • ระบบข้อสอบมี traffic แบบพุ่งช่วงสอบ ควรออกแบบ connection pooling (Supabase มี Supavisor ให้) และ cache สถิติด้วย materialized view ตั้งแต่แรก
  • ถ้าภายหลังข้อมูลใหญ่มาก สามารถทำ analytics หนักบน replica แยกได้ เพราะเป็น Postgres มาตรฐาน เส้นทางขยายตัวเปิดกว้างกว่า Firestore

สรุปรวบ

ระบบที่อธิบายคือ "application ที่มีข้อมูลเชิงสัมพันธ์ + analytics หนัก + AI ที่ต้องค้นหาข้อมูลเชิงความหมาย" ซึ่งเป็นจุดแข็งสามอย่างพร้อมกันของ Supabase ส่วน Firebase เหมาะกว่าเฉพาะกรณีที่เน้น mobile app แบบ offline-first ล้วน ๆ ซึ่งไม่ใช่ลักษณะงานนี้

5 · เนื้อหาเสริม

5.1 โมเดลการให้คะแนน Adaptive ที่ใช้ได้จริงกับ Postgres

นอกจาก IRT และ Elo rating ควรพิจารณา Bayesian Knowledge Tracing (BKT) ด้วย เพราะคำนวณง่ายกว่า IRT และเก็บ state เป็นเพียงค่า float ต่อคู่ (student, topic) เหมาะกับตาราง Postgres ธรรมดา ไม่ต้องพึ่ง library ML หนัก

5.2 Edge Function กับ Rate Limit ของ LLM API

เมื่อใช้ Supabase Edge Function เรียก LLM เพื่อ generate ข้อสอบ ควรออกแบบเป็น job queue เช่นใช้ตารางร่วมกับ pg_cron poll แทนการเรียกแบบ synchronous ตรง ๆ เพราะการ generate ข้อสอบพร้อมภาพอาจใช้เวลานาน และป้องกัน timeout ของ Edge Function ที่ปกติจำกัดไม่กี่สิบวินาที

5.3 การจัดการภาพข้อสอบขนาดใหญ่

ถ้าภาพประกอบมีจำนวนมากและต้องโหลดเร็วพร้อมกันหลายคนช่วงสอบ ควรพ่วง CDN เช่น Cloudflare หน้า Supabase Storage และตั้ง cache header ให้เหมาะสม เพราะ traffic พุ่งพร้อมกันช่วงสอบเป็นจุดเสี่ยงคอขวดจริง

5.4 ทางเลือกอื่นที่ควรรู้จักไว้เผื่อเทียบ

  • Neon / PlanetScale (Postgres/MySQL serverless) — คล้าย Supabase แต่เน้น database branching ล้วน ๆ ไม่มี Auth/Storage/Edge Function ในตัว ต้องประกอบเองมากกว่า
  • ถ้าองค์กรมีข้อจำกัดด้าน data residency เช่นข้อมูลนักเรียนต้องอยู่ในประเทศ ควรเช็คว่า Supabase self-host หรือเลือก region ที่ต้องการได้หรือไม่
